# 药品管理最小演示系统项目报告

## 摘要

随着医院药房和门诊诊疗业务逐步走向信息化，药品库存可视化、补货操作留痕和处方用药合规控制成为基层医疗软件中的高频需求。传统依赖纸质登记或分散式表格的管理方式，容易出现库存数据更新不及时、低库存风险发现滞后、处方药权限边界不清晰等问题，影响药品管理效率和演示教学效果。因此，设计并实现一个面向药房场景的药品管理最小演示系统，具有较好的实践意义与应用价值。

本文围绕“库存预览、药物入库、医生开药”三个核心业务，完成了如下工作：

- 设计并实现基于 Spring Boot、MyBatis、MySQL 和 React 的前后端分离药品管理系统；
- 按最小演示闭环收缩系统功能范围，形成医生与药师两类角色的清晰权限边界；
- 完成药品、库存、库存流水、处方、预警、用户账号等核心数据表设计与初始化脚本编写；
- 实现库存分页查询、低库存预警查询、库存入库、处方创建与自动扣减库存等关键业务流程；
- 基于 Docker Compose 设计单机容器化部署方案，支撑项目在答辩或展示环境中的快速启动；
- 结合单元测试、H2 集成测试和构建验证，对系统核心链路进行功能性检查。

本文的主要特色在于：提出了一种面向课程设计和现场展示的“最小演示闭环”实现思路，将原本复杂的药房业务收敛为库存查看、入库补货和医生开药三条主链路，在保证角色边界和库存联动规则正确的基础上，降低了系统使用复杂度与演示失败风险。系统目前已完成前后端主要功能实现、基础测试与容器化部署结构搭建，能够支持医生账号完成开药演示、支持药师账号完成库存查看与入库演示，具备较好的可运行性；但在并发压测、完整工作流扩展和自动化端到端测试方面仍有进一步完善空间。

**关键词：** 药品管理系统；库存预览；处方管理；Spring Boot；React；Docker Compose；角色权限控制

## Abstract

With the continuous informatization of hospital pharmacies and outpatient services, inventory visibility, replenishment traceability, and prescription compliance control have become common requirements in medical software. Traditional management methods based on paper records or scattered spreadsheets often lead to delayed inventory updates, late discovery of low-stock risks, and unclear authority boundaries for prescription drugs. Therefore, it is meaningful to design and implement a lightweight drug management demo system for pharmacy scenarios.

This project focuses on three core business functions: inventory overview, drug inbound, and doctor prescription. The main work includes: designing and implementing a front-end and back-end separated system based on Spring Boot, MyBatis, MySQL, and React; narrowing the system scope to a minimal demo workflow with clear role boundaries for doctors and pharmacists; designing core database tables and initialization scripts for drugs, inventories, inventory records, prescriptions, warnings, and user accounts; implementing key business processes such as inventory query, low-stock warning query, drug inbound, prescription creation, and automatic inventory deduction; preparing a single-machine containerized deployment solution with Docker Compose; and verifying the main system flow through unit tests, H2 integration tests, and build checks.

The main feature of this work is a minimal-demo-oriented implementation strategy. Instead of presenting a full and complex pharmacy platform, the project extracts three representative business flows to improve demo efficiency while keeping core rules correct. At present, the system has completed its main front-end and back-end implementation, basic testing, and deployment structure. It can support doctor prescription demonstrations and pharmacist inventory operations, while future improvements are still needed in concurrency evaluation, complete workflow expansion, and end-to-end automation.

**Keywords:** drug management system, inventory overview, prescription management, Spring Boot, React, Docker Compose, role-based access control

## 第一章 绪论

### 1.1 论文工作背景与意义

药品管理是医院门诊、住院药房以及基层医疗机构中的基础业务。无论是药品采购入库、库存维护，还是医生处方开具与药品发放，都依赖准确、及时且可追踪的数据支持。如果库存账实不一致、低库存预警缺失，或者处方药权限控制不严，就会直接影响药房工作效率，甚至带来管理风险。

在实际教学和课程设计场景中，完整的医院药房系统往往包含药品档案管理、库存盘点、预警工作台、处方审核、药师发药、权限审批、统计报表等大量模块。对于时间有限的课程设计或答辩演示而言，若将所有功能同时展开，容易造成页面复杂、链路分散、测试难度大、演示不稳定等问题。因此，需要在保留核心业务逻辑的基础上，对系统功能进行合理收口，构建一套“小而完整”的药品管理演示系统。

本课题的意义主要体现在以下几个方面。

1. 有助于验证药品库存与处方业务之间的联动关系。通过入库增加库存、开药扣减库存，可以展示业务数据前后关联。
2. 有助于体现医疗系统中角色权限控制的重要性。系统将医生与药师权限区分开来，保证处方药只能由医生开具。
3. 有助于在有限开发周期内完成可演示、可部署、可测试的完整软件作品。通过功能收口，增强项目的实现质量和答辩可控性。
4. 有助于为后续扩展完整药房管理平台奠定基础。当前系统虽然聚焦最小闭环，但已经具备清晰的分层架构、数据库结构和接口基础。

### 1.2 相关研究现状

当前与本文工作相关的研究与实践，主要集中在医疗信息系统、药房管理系统、库存管理系统以及前后端分离 Web 应用架构等几个方向。

第一，医院信息系统与药房管理系统研究较多关注完整业务覆盖能力。例如药品档案维护、采购管理、库存管理、处方审核与发药流转等。这类系统通常强调功能完备性、流程规范性和多角色协同能力，但实现复杂度较高，更适合真实生产环境，不完全适合课程设计中的快速演示目标。

第二，库存管理类系统研究通常围绕库存预警、先进先出、批次管理和效期控制展开。药品属于强监管、高敏感度物资，其库存管理不仅要求数量准确，还要求记录批次号、有效期和操作流水。本文系统在库存模块中吸收了这些常见思路，支持按药品、批次和效期维护库存，并通过低库存预警提升可视化效果。

第三，Web 应用架构研究已普遍采用前后端分离方式。Spring Boot 因其开发效率高、生态成熟，广泛应用于中小型信息管理系统后端开发；React 则因组件化能力强、前端交互灵活而被广泛使用。本文采用 Spring Boot + MyBatis + React 的技术路线，能够兼顾开发效率、结构清晰度与课程项目落地可行性。

第四，近年来容器化部署在教学项目和中小型交付项目中应用广泛。Docker Compose 可以将数据库、后端、前端和反向代理统一编排，降低部署门槛，提高环境一致性。本文在部署方案中采用 Compose，对最终交付和答辩环境切换有较强实用价值。

综合来看，已有研究为本文提供了较成熟的技术基础和设计思路，但多数工作更偏向复杂生产系统或泛化库存系统。本文与其不同之处在于，以“最小演示闭环”为导向，在保留药品管理核心规则的前提下，强调功能收口、角色边界明确和演示路径清晰，使系统更契合课程设计场景。

## 第二章 相关技术基础

### 2.1 Spring Boot 技术基础

Spring Boot 是当前 Java Web 开发中常用的快速开发框架，具备自动配置、依赖整合方便、项目结构清晰等特点。本文后端采用 Spring Boot 3.3.1 作为核心框架，实现接口开发、参数校验、异常处理、事务管理和应用启动配置。通过使用 Spring Boot，可以降低项目样板代码量，提高系统开发效率。

### 2.2 MyBatis 持久层技术

MyBatis 是一种轻量级持久层框架，适合对 SQL 语句有明确控制需求的管理信息系统。本文使用 MyBatis 进行数据库访问，结合 Mapper 接口与 XML 映射文件实现药品、库存、处方和预警等业务查询与写入。相比全自动 ORM 方案，MyBatis 更便于根据药品库存业务编写精细化 SQL，例如按效期排序扣减库存、低库存统计等。

### 2.3 MySQL 数据库技术

MySQL 8.x 是当前广泛使用的关系型数据库，具有稳定、易部署、生态成熟等优点。本文以 MySQL 作为生产演示环境数据库，负责持久化药品信息、库存信息、处方数据和操作流水。为了保证中文数据和容器环境初始化的一致性，项目在建表与种子脚本中统一设置了 `utf8mb4` 字符集相关配置。

### 2.4 React 前端技术

React 是一种基于组件的前端开发框架，适用于构建交互式单页应用。本文前端基于 React 18 和 Vite 实现，负责完成登录页、主页、库存预览页、药物入库页和开药页的交互展示。系统通过路由控制和角色判断，在前端层面实现医生与药师页面入口差异化，提升演示直观性。

### 2.5 Vite 与前端工程化

Vite 是轻量化前端构建工具，具备启动快、热更新效率高、生产构建简单等特点。本文使用 Vite 管理前端项目结构、开发服务和生产打包流程，并结合 Vitest 完成基础前端测试。该方案适合课程设计中的快速开发和本地调试。

### 2.6 Docker Compose 容器编排技术

Docker Compose 可用于定义和运行多容器应用。本文将 MySQL、后端 Spring Boot、前端 React 和 Nginx 统一纳入 Compose 编排，形成标准化演示环境。相比手动逐个部署，Compose 能够提升环境一致性，降低部署步骤复杂度，适合课程答辩或项目交付展示。

### 2.7 角色权限控制与请求拦截

药品管理系统中的角色权限控制是业务正确性的关键。本文通过后端拦截器读取登录态或请求头，解析当前用户身份，并在开药等关键接口中进行角色校验。医生角色具备开药能力，药师角色不具备该权限。该设计既体现了业务规则，又简化了认证实现复杂度。

### 2.8 本章小结

本章介绍了本文系统开发所依赖的主要技术，包括 Spring Boot、MyBatis、MySQL、React、Vite、Docker Compose 以及角色权限控制机制。这些技术共同构成了系统的实现基础，为后续需求分析、系统设计与实现提供了支撑。

## 第三章 系统需求分析

### 3.1 系统功能需求分析

#### 3.1.1 用户角色分析

根据当前项目定位，系统只保留两类角色：

1. 医生
2. 药师

医生主要负责开具处方，并可查看库存和执行入库演示；药师主要负责查看库存和执行药品入库，不参与处方药开具。

#### 3.1.2 医生角色功能需求

医生角色需要满足以下功能需求：

1. 登录系统并进入简化主页。
2. 查看库存预览，包括药品名称、库存数量、批次号、有效期和低库存状态。
3. 执行药物入库操作，录入药品、批次、有效期、数量、库位和业务单号等信息。
4. 在开药页面录入患者姓名、药品、剂量、频次、天数和数量，提交处方。
5. 处方提交后，系统能够自动扣减相应库存，并记录库存流水。

文字化用例说明如下：

- 用例 1：医生登录系统
- 用例 2：医生查询库存信息
- 用例 3：医生执行药品入库
- 用例 4：医生开具处方药
- 用例 5：系统自动扣减库存并记录发药流水

#### 3.1.3 药师角色功能需求

药师角色需要满足以下功能需求：

1. 登录系统并进入简化主页。
2. 查看库存预览及低库存提醒。
3. 执行药物入库操作，补充库存。
4. 不显示开药入口，也不能发起处方药开具。

文字化用例说明如下：

- 用例 1：药师登录系统
- 用例 2：药师查询库存信息
- 用例 3：药师执行药品入库
- 用例 4：药师访问开药功能时被前后端权限限制

#### 3.1.4 系统核心功能需求归纳

根据当前项目收口目标，系统核心功能需求可概括为三项：

1. 库存预览
2. 药物入库
3. 开药

其中，库存预览页面需要同时展示库存列表和低库存提醒；药物入库页面负责完成补货操作；开药页面只允许医生使用，并在提交后自动联动库存扣减。

### 3.2 系统非功能需求分析

#### 3.2.1 性能需求

考虑到本系统主要面向课程设计答辩、演示和单机运行，性能需求以稳定性和基本响应速度为主，具体指标如下：

1. 登录、库存查询、低库存查询等常用接口在单机演示环境下平均响应时间不超过 2 秒。
2. 入库和开药等写操作在无明显网络波动条件下响应时间不超过 3 秒。
3. 前端页面首次加载后，路由切换与数据刷新应保持可接受的交互流畅度。

#### 3.2.2 并发访问需求

本系统当前不以高并发生产场景为目标，而以单机演示和少量并发访问为主。设计目标如下：

1. 能支撑 5 至 10 个并发请求下的基本稳定运行。
2. 在库存扣减、入库写入等事务场景中，保证单次业务操作数据一致性。
3. 后续若面向更大规模部署，需要补充专门的并发测试、锁机制优化和数据库调优。

#### 3.2.3 安全性与可靠性需求

1. 非健康检查接口必须带有当前用户身份信息或登录态。
2. 开药接口必须校验当前用户角色，拒绝药师越权访问。
3. 写操作应产生库存流水或处方记录，保证关键业务可追踪。
4. 容器化部署时，数据库、后端、前端和 Nginx 服务应具备基础健康检查与启动顺序控制。

#### 3.2.4 可维护性需求

1. 系统需具备清晰的前后端分层结构。
2. 核心业务规则应集中在服务层，便于后续扩展。
3. 项目需配套架构、部署、测试和范围说明文档，便于后续维护和交接。

### 3.3 本章小结

本章从功能需求和非功能需求两个方面对系统进行了分析，明确了医生和药师两类角色的业务边界，以及库存预览、药物入库、开药三项核心功能目标。同时提出了性能、并发、安全性和可维护性方面的基本要求，为后续系统设计与实现提供了依据。

## 第四章 系统设计

### 4.1 系统总体设计

#### 4.1.1 系统分层结构设计

本文系统采用前后端分离架构，可划分为以下三层：

1. 交互层
2. 核心业务层
3. 数据存储层

各层职责如下：

1. 交互层：由 React 前端页面和 Nginx 入口组成，负责用户登录、页面展示、表单提交和结果反馈。
2. 核心业务层：由 Spring Boot 后端构成，负责处理库存查询、低库存预警、入库写入、处方开具、角色校验和异常处理等业务逻辑。
3. 数据存储层：由 MySQL 数据库构成，负责持久化药品、库存、库存流水、处方、处方明细和用户账号等数据。

#### 4.1.2 系统功能模块结构设计

系统主要包含以下模块：

1. 用户认证与身份识别模块
2. 药品管理模块
3. 库存管理模块
4. 预警查询模块
5. 处方管理模块
6. 前端页面展示模块
7. 部署与运行支撑模块

其中：

#### 4.1.3 系统总体工作流程设计

系统当前主流程可分为三条：

1. 登录与角色识别流程
2. 药品入库流程
3. 医生开药与库存联动流程

登录与角色识别流程如下：

1. 用户输入 `userId` 和密码。
2. 前端调用登录接口。
3. 后端校验用户账号和密码，返回用户信息及会话标识。
4. 前端保存当前会话，并根据角色动态展示页面入口。

药品入库流程如下：

1. 用户进入入库页面。
2. 前端加载可选药品和最近库存记录。
3. 用户填写药品、批次号、有效期、数量、库位和备注等信息后提交。
4. 后端校验药品是否存在。
5. 若相同药品、批次和效期库存已存在，则累加数量；否则新建库存记录。
6. 后端写入一条入库流水。
7. 前端提示入库成功，并刷新近期库存数据。

医生开药与库存联动流程如下：

1. 医生进入开药页面。
2. 前端加载可开具药品列表。
3. 医生填写患者姓名、药品、剂量、频次、天数和数量后提交。
4. 后端校验当前用户必须为医生角色。
5. 后端保存处方主表和处方明细数据。
6. 系统按药品查询可用库存，按照最早到期批次优先扣减。
7. 扣减成功后写入发药库存流水，并将处方状态更新为已发药。
8. 若库存不足，则拒绝本次业务并返回业务规则错误。

主要接口设计包括：

1. `POST /api/auth/login`：登录接口。
2. `GET /api/inventories`：库存分页查询接口。
3. `GET /api/warnings/low-stock`：低库存预警查询接口。
4. `POST /api/inventories/inbound`：药物入库接口。
5. `POST /api/prescriptions`：处方创建接口。

#### 4.1.4 系统数据库设计

从当前系统业务需要出发，核心数据库表主要包括：

1. `user_account`：用户账号表，保存用户编号、姓名、角色、密码、启用状态等信息。
2. `drug`：药品表，保存药品编码、药品名称、单位、价格、低库存阈值和分类信息。
3. `inventory`：库存表，保存药品、批次号、有效期、库存数量、锁定数量和库位信息。
4. `inventory_record`：库存流水表，保存入库、出库、盘点、发药等操作记录。
5. `prescription`：处方主表，保存处方编号、患者姓名、医生信息、状态和备注。
6. `prescription_item`：处方明细表，保存单个处方中的药品、剂量、频次、天数和数量。

表之间的主要关系如下：

3. `prescription` 与 `prescription_item` 为一对多关系，一张处方可包含多个药品明细。
4. `drug` 与 `prescription_item` 为一对多关系，处方明细关联具体药品。
5. `user_account` 与 `prescription` 之间通过医生编号建立关联。

#### 4.2.3 处方管理模块详细设计

处方管理模块是系统最具业务特征的模块。当前最小闭环将复杂的“提交-审核-发药”流程简化为“医生创建处方后直接完成库存扣减和处方发药状态更新”，以突出药品业务联动。

详细流程如下：

1. 校验当前用户必须为医生。
2. 创建处方主表记录，生成处方编号。
3. 遍历处方明细，逐项校验药品是否存在。
4. 写入处方明细数据。
5. 查询该药品的可用库存列表，并按效期升序排列。
6. 按先进先出原则逐批次扣减库存。
7. 为每次扣减写入发药流水记录。
8. 若任意药品库存不足，则抛出异常并回滚事务。
9. 所有药品扣减完成后，将处方状态更新为已发药。

### 4.3 核心算法设计

本文系统的核心算法主要体现在库存扣减策略上，即处方发药时对多个库存批次的有序消耗逻辑。该策略虽然不属于复杂数学算法，但属于典型的业务规则算法，其正确性直接影响系统演示结果。

#### 4.3.1 基于最早到期优先的库存扣减算法

算法思想如下：

1. 根据处方明细中的药品 ID，查询所有可用库存批次。
2. 按药品有效期从早到晚排序。
3. 依次遍历库存批次，优先消耗最早到期的一批。
4. 若当前批次数量足够，则直接扣减并结束。
5. 若当前批次数量不足，则全部消耗该批次，继续扣减下一批。
6. 若遍历结束后仍存在未满足数量，则判定库存不足并回滚事务。

该策略的优点包括：

1. 符合药品效期优先使用的一般管理原则。
2. 可减少临期药品积压风险。
3. 逻辑清晰，适合课程项目中展示业务规则实现。

伪代码描述如下：

```text
remaining = 处方所需数量
inventories = 查询药品可用库存并按有效期升序排序
for inventory in inventories:
    if remaining <= 0:
        break
    consume = min(remaining, inventory.quantity)
    扣减当前批次 consume
    写入发药流水
    remaining = remaining - consume
if remaining > 0:
    抛出库存不足异常并回滚事务
```

#### 4.3.2 算法实现价值分析

该算法在系统中的价值主要体现在：

1. 体现了药房库存管理的业务合理性。
2. 与处方开具流程形成了明显的数据联动效果。
3. 能够通过库存数量变化和库存流水结果直观展示系统核心能力。

本章围绕系统设计展开，分别介绍了系统分层结构、功能模块、工作流程、数据库设计以及库存扣减核心算法。通过这些设计，系统能够在较小规模下完成库存预览、药物入库与医生开药三条主链路，为后续实现与测试奠定了基础。

### 5.2 核心代码分析

#### 5.2.1 基于拦截器的当前用户识别实现

后端通过 `AuthInterceptor` 统一解析请求头中的当前用户信息，并写入 `CurrentUserHolder`。该实现的作用是让后续服务层无需重复解析请求参数，即可获得当前登录用户身份。

核心思路如下：

1. 对 `OPTIONS` 预检请求直接放行，避免跨域预检失败。
2. 优先解析 `Authorization: Bearer ...` 登录态。
3. 若无 Bearer Token，则读取 `X-User-Id`、`X-User-Name`、`X-User-Role`。
4. 对中文用户名进行 URL 解码后写入当前用户上下文。
5. 请求完成后清理线程上下文。

该设计的优势是实现简单、适合演示，并能兼容容器环境下的同源接口访问。

#### 5.2.2 库存入库逻辑实现

库存入库逻辑位于 `InventoryServiceImpl` 中，核心实现思想是“同药品、同批次、同效期合并库存，否则新建库存记录”，并始终写入库存流水。

主要实现步骤包括：

1. 调用 `ensureDrugExists` 校验药品是否存在。
2. 通过 `findByDrugBatchAndExpiry` 查询是否已有相同批次库存。
3. 若无记录则插入新的 `inventory` 数据。
4. 若已有记录则更新数量。
5. 调用 `writeRecord` 记录本次入库操作前后数量和业务单号。

这一实现保证了库存展示数据与库存流水数据同步，便于后续追踪操作历史。

#### 5.2.3 医生开药与自动扣减库存实现

处方开具逻辑位于 `PrescriptionServiceImpl` 中，是系统最核心的代码实现之一。其业务特征体现在角色校验、事务处理和多批次库存扣减三个方面。

主要逻辑包括：

1. 使用 `requireCurrentUser` 获取当前登录用户。
2. 判断角色是否为 `DOCTOR`，若不是则直接拒绝。
3. 创建处方主表和处方明细。
4. 调用 `dispensePrescriptionItems` 按批次扣减库存。
5. 每次扣减完成后写入一条类型为 `DISPENSE` 的库存流水。
6. 所有明细处理完成后，将处方状态更新为 `DISPENSED`。

由于该方法加上了事务控制，一旦库存不足或中途发生异常，系统可以整体回滚，避免出现“处方已创建但库存未正确扣减”的不一致状态。

3. 项目文档中已记录 `mvn clean test`、`npm run test` 和 `npm run build` 的验证路径。

通过上述功能测试，系统当前能够满足最小演示功能需求目标。

### 5.4.3 系统非功能测试

受课程项目时间与环境限制，当前系统未进行大规模压测，但已从部署与运行稳定性角度开展基础非功能验证，内容如下：

1. 可构建性验证：后端支持 Maven 构建，前端支持 Vite 生产构建。
2. 可部署性验证：项目提供 Docker Compose 编排文件，可统一启动 MySQL、后端、前端和 Nginx。
3. 可维护性验证：项目具备架构、前端范围、部署、测试和接口文档，可支撑后续迭代。
4. 编码一致性验证：针对中文数据链路，已统一后端、数据库初始化脚本和连接参数字符集设置。

当前非功能指标结论如下：

1. 在单机演示环境下，系统满足基本响应和部署要求。
2. 项目具备清晰的模块划分和文档配套，具备较好的维护性。
3. 真实高并发性能、自动化端到端回归和安全加固尚未充分验证，属于后续改进重点。

### 5.5 本章小结

本章从实现工具与环境、核心代码分析、主要运行界面和系统测试四个方面介绍了项目的实际落地情况。当前系统已完成库存预览、药物入库和医生开药三条核心链路实现，并具备基础测试与容器化部署能力，能够支撑课程设计中的答辩与演示需求。

## 第六章 总结与展望

### 6.1 总结

本文围绕药房场景下的药品管理需求，设计并实现了一个面向课程设计演示的药品管理最小演示系统。系统采用 Spring Boot、MyBatis、MySQL、React 和 Docker Compose 等技术，完成了前后端分离架构设计、数据库设计、核心业务实现和基础测试验证。

本文完成的主要成果包括：

1. 提出并落地了一种“最小演示闭环”的药品管理系统实现思路，将系统展示范围收缩为库存预览、药物入库和医生开药三项核心功能。
2. 实现了医生与药师两类角色的权限边界控制，使处方药开具能力只向医生开放。
3. 设计并实现了库存与处方联动机制，支持医生开药后自动扣减库存并写入库存流水。
4. 构建了适合课程项目交付的单机容器化部署方案，降低了项目演示与复现实验环境的成本。
5. 完成了相关文档、初始化数据与基础测试，为后续扩展完整药房管理平台奠定了基础。

总体来看，系统已达到“可运行、可演示、可扩展”的阶段性目标，能够较好体现药品管理业务中的库存可视化、补货操作和处方权限控制等核心问题。

### 6.2 展望

尽管当前系统已实现预期的最小演示目标，但仍存在以下不足与改进空间：

1. 认证与权限控制仍较轻量，后续可引入更完整的 JWT 或 Spring Security 方案。
2. 当前前端只保留三项主演示功能，完整处方审核、发药工作台、库存盘点和药品 CRUD 页面尚未作为主演示内容恢复。
3. 系统尚未开展系统化并发测试和压力测试，库存竞争场景下的性能表现仍需进一步评估。
4. 自动化测试覆盖率仍有限，后续应补充入库接口、处方扣库存链路、越权访问和前后端联调回归测试。
5. 界面层目前以功能演示为主，后续可继续优化交互体验、统计展示和可视化效果。

未来工作可从“完善认证安全体系、扩展完整药房工作流、补强自动化测试、提升界面质量和加强性能验证”等方向继续推进。
