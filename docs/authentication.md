# 认证方案说明

## 1. 目标

本方案只服务于项目主功能落地，不追求复杂权限体系。

当前认证设计只需要满足：

- 区分医生与药师两类角色
- 让后端知道当前操作人是谁
- 支撑处方授权、审核、发药等关键角色限制
- 便于前端联调与最终演示

## 2. 当前业务约束

当前后端已经依赖以下身份信息：

- 用户 ID
- 用户姓名
- 用户角色

其中角色仅保留两类：

- `DOCTOR`
- `PHARMACIST`

## 3. 当前阶段推荐方案

为了尽快落地项目，推荐采用“轻量登录态 + 请求头透传”的方案。

即：

1. 前端提供一个简化登录入口
2. 用户选择身份后，前端保存当前用户信息
3. 后续请求统一携带当前用户头信息
4. 后端从请求头中解析当前用户

推荐请求头：

- `X-User-Id`
- `X-User-Name`
- `X-User-Role`

## 4. 当前已落地实现

当前仓库已经完成最小认证基线：

- 后端通过拦截器统一拦截 `/api/**`
- `GET /api/health` 作为健康检查接口保留匿名访问
- 其余 API 当前都要求携带：
  - `X-User-Id`
  - `X-User-Name`
  - `X-User-Role`
- 后端会把请求头解析为当前用户上下文
- 非法角色或缺失请求头会返回 `4010 unauthorized`
- 后端已提供 `GET /api/auth/me` 作为联调校验接口
- 前端已提供最小登录入口，支持在医生与药师演示身份之间切换
- 前端当前用户状态默认保存在本地存储；测试环境下回退为内存存储

## 5. 为什么采用这个方案

当前项目目标是完成主功能并可演示，不是先做完整安全体系。

采用该方案的原因：

- 落地成本低
- 不依赖完整用户表与密码体系
- 足以支撑当前医生/药师角色边界
- 前后端联调简单
- 后续如需升级到 JWT 或 Session，可平滑替换

## 6. 后端落地要求

后端后续需要补以下内容：

### 6.1 当前用户上下文对象

建议增加统一的当前用户对象，字段至少包括：

- `userId`
- `userName`
- `role`

### 6.2 请求头解析

建议在拦截器或过滤器中统一解析请求头：

- 校验头信息是否完整
- 校验角色是否合法
- 将当前用户写入上下文

### 6.3 业务字段收口

后端后续应逐步把以下字段从“前端请求体显式传值”改为“后端从当前用户注入”：

- `createdByUserId`
- `createdByName`
- `createdByRole`
- `operatorId`
- `operatorName`

说明：

- `doctorId` 和 `doctorName` 在药师代开场景仍然可能需要前端显式选择
- 但“当前操作者是谁”不应长期由前端自由填写

## 7. 前端落地要求

前端后续需要补以下内容：

### 7.1 登录页

当前阶段只需要一个简化登录页，支持：

- 选择医生身份登录
- 选择药师身份登录

### 7.2 本地保存

前端可以先将当前用户保存到：

- `localStorage`
  或
- 全局状态

保存字段至少包括：

- `userId`
- `userName`
- `role`

### 7.3 请求封装

所有 API 请求统一通过请求封装层自动附带：

- `X-User-Id`
- `X-User-Name`
- `X-User-Role`

## 8. 最小演示身份建议

为了快速演示，建议先固定两组身份：

- 医生
  - `userId=100`
  - `userName=王医生`
  - `role=DOCTOR`
- 药师
  - `userId=200`
  - `userName=张药师`
  - `role=PHARMACIST`

## 9. 当前阶段剩余工作

在认证主题下，当前仍需继续完成：

1. 前端统一请求封装，并自动附加当前用户请求头
2. 处方、库存等关键业务逐步改为从当前用户上下文注入操作者字段
3. 前后端联调时补充未登录、非法角色、切换身份等场景验证
4. Docker 演示环境中验证 `/api/auth/me` 与主业务接口请求头透传

## 10. 后续升级路径

如果项目进入更正式阶段，可按以下顺序升级：

1. 增加用户表
2. 增加账号密码登录
3. 使用 JWT 或 Session
4. 增加更细粒度权限控制

当前阶段不建议先做这一步，以免偏离主功能落地目标。
