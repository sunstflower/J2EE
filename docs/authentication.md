# 认证方案说明

## 1. 目标

本方案只服务于项目主功能落地，不追求复杂权限体系。

当前认证设计只需要满足：

- 区分医生与药师两类角色
- 让后端知道当前操作人是谁
- 支撑处方授权、审核、发药等关键角色限制
- 便于前端联调与最终演示

## 2. 当前业务约束

当前后端已经依赖以下身份信息：

- 用户 ID
- 用户姓名
- 用户角色

其中角色仅保留两类：

- `DOCTOR`
- `PHARMACIST`

## 3. 当前阶段方案

为了尽快落地项目，当前采用“后端登录签发演示会话 + 前端持有 token”的轻量认证方案。

即：

1. 前端进入系统前先展示登录 / 注册页
2. 登录由后端 `POST /api/auth/login` 完成
3. 注册由后端 `POST /api/auth/register` 完成
4. 前端只保存当前 token 和当前用户，不在浏览器保存明文密码
5. 后续请求优先通过 `Authorization: Bearer <token>` 传递登录态
6. 后端从 token 解析当前用户上下文

## 4. 当前已落地实现

当前仓库已经完成最小认证基线：

- 后端通过拦截器统一拦截 `/api/**`
- `GET /api/health` 作为健康检查接口保留匿名访问
- 后端已提供：
  - `POST /api/auth/login`
  - `POST /api/auth/register`
  - `GET /api/auth/me`
- 前端登录成功后保存：
  - `token`
  - `userId`
  - `userName`
  - `role`
- 前端请求封装层会自动附带：
  - `Authorization: Bearer <token>`
- 为兼容已有业务联调代码，后端当前仍兼容：
  - `X-User-Id`
  - `X-User-Name`
  - `X-User-Role`
- token 无效、缺失身份上下文或角色非法时，后端返回 `4010 unauthorized`
- 前端已接入登录 / 注册页、主路由守卫与角色提示

## 5. 为什么采用这个方案

当前项目目标是完成主功能并可演示，不是先做完整安全体系。

采用该方案的原因：

- 落地成本低
- 已具备基本账号密码入口，便于演示
- 足以支撑当前医生/药师角色边界
- 前后端联调简单
- 后续如需切到数据库用户表、JWT 或正式 Session，可继续演进

## 6. 后端落地要求

后端当前已落地统一的当前用户上下文解析，后续仍需继续补以下内容：

### 6.1 当前用户上下文对象

建议增加统一的当前用户对象，字段至少包括：

- `userId`
- `userName`
- `role`

### 6.2 请求头解析

当前已在拦截器中统一解析：

- `Authorization: Bearer <token>`
- 兼容旧的 `X-User-*` 请求头

后续仍应继续增强：

- token 生命周期和失效策略
- 密码加密存储，而不是当前演示态明文
- 更明确的匿名白名单与角色权限边界

### 6.3 业务字段收口

后端后续应继续把以下字段从“前端请求体显式传值”改为“后端从当前用户注入”：

- `createdByUserId`
- `createdByName`
- `createdByRole`
- `operatorId`
- `operatorName`

说明：

- `doctorId` 和 `doctorName` 在药师代开场景仍然可能需要前端显式选择
- 但“当前操作者是谁”不应长期由前端自由填写
- 当前库存服务以及处方的创建、审核、发药、医生授权环节，已经优先以后端认证上下文为准

## 7. 前端落地要求

前端当前已完成最小登录 / 注册入口，后续需要继续补以下内容：

### 7.1 登录页

当前阶段登录页已支持：

- 登录
- 注册
- 根据用户号首位提示角色

当前约束：

- `1` 开头为药师
- `2` 开头为医生

### 7.2 本地保存

前端当前保存到本地存储或测试环境内存中的字段包括：

- `token`
- `user`
  - `userId`
  - `userName`
  - `role`

### 7.3 请求封装

所有 API 请求统一通过请求封装层自动附带：

- `Authorization: Bearer <token>`

说明：

- 当前前端不再自行拼装 `X-User-*` 作为主认证方式
- 旧请求头兼容主要用于过渡和排障

## 8. 最小演示身份建议

为了快速演示，当前默认保留两组身份：

- 医生
  - `userId=2001`
  - `userName=王医生`
  - `password=doctor123`
  - `role=DOCTOR`
- 药师
  - `userId=1001`
  - `userName=张药师`
  - `password=pharm123`
  - `role=PHARMACIST`

## 9. 当前阶段剩余工作

在认证主题下，当前仍需继续完成：

1. 将演示账号密码从明文存储升级为加密存储
2. 继续检查其余业务接口，确保不再依赖前端自由传递操作者身份字段
3. 补齐角色级路由体验拦截与后端权限测试
4. Docker 演示环境中完成登录、注册、鉴权失败、退出登录的实跑验证

## 10. 后续升级路径

如果项目进入更正式阶段，可按以下顺序升级：

1. 增加用户表与密码加密
2. 将演示 token 改为可过期会话或 JWT
3. 增加刷新机制与注销失效
4. 增加更细粒度权限控制

当前阶段不建议先做这一步，以免偏离主功能落地目标。
