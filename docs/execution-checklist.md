# 项目执行清单

## 1. 目标

本清单用于把现有设计文档收敛成可直接执行的落地步骤。

执行原则：

- 只围绕主功能闭环推进
- 每一步都要有明确产出
- 每一步都要有最低验收标准

## 2. 当前基线

当前已经完成：

- 后端药品模块
- 后端库存模块
- 后端预警模块
- 后端处方模块
- 最小认证基线后端接入
- 前端最小登录入口
- 数据库初始化脚本
- 后端单元测试与 H2 集成测试基线
- 前端基础页面测试基线
- Docker 骨架
- API、测试、演示、认证、联调、部署文档基础说明

当前未完成：

- 前端统一请求头注入
- 基于角色的前端业务页面实现
- 前后端联调
- Docker 演示环境实操验证
- 最终部署交付验证

## 3. 执行总顺序

后续工作按以下顺序执行：

1. 认证基线收口
2. 前端主页面落地
3. 前后端联调
4. Docker 演示验证
5. 部署验证

## 4. 分阶段执行清单

### 阶段一：认证接入

目标：

- 建立当前用户概念
- 区分医生与药师身份
- 为处方授权、审核、发药提供真实操作者上下文

执行项：

- 已完成：
  - 增加当前用户上下文对象
  - 增加请求头解析拦截器
  - 统一解析：
    - `X-User-Id`
    - `X-User-Name`
    - `X-User-Role`
  - 增加 `GET /api/auth/me` 联调接口
  - 增加前端最小登录入口
- 待完成：
  - 前端统一请求封装并自动附带请求头
  - 后端逐步改造创建人和操作人信息由上下文注入
  - 补充前后端联调验证记录

产出物：

- 认证相关代码
- 对应测试
- 文档更新

验收标准：

- 医生请求可识别为医生
- 药师请求可识别为药师
- 非法角色请求被拒绝
- 前端登录后可稳定切换演示身份
- 处方关键操作不再依赖前端手填操作者字段

参考文档：

- `docs/authentication.md`

### 阶段二：前端主页面落地

目标：

- 让主功能具备页面入口
- 为联调和演示提供可操作界面

执行项：

- 登录页
- 首页
- 药品列表页
- 库存管理页
- 库存流水页
- 预警页
- 处方列表页
- 处方创建页
- 处方详情页

产出物：

- 页面代码
- 基础组件
- 前端测试
- 文档更新

验收标准：

- 页面可访问
- 列表可展示
- 表单可提交
- 状态可区分
- 医生和药师看到的关键操作入口不同

参考文档：

- `docs/frontend-integration.md`
- `docs/api.md`

### 阶段三：前后端联调

目标：

- 让页面与真实 API 打通
- 让主功能链路可以从前端完整走通

执行项：

- 登录后统一注入当前用户请求头
- 联调药品模块
- 联调库存模块
- 联调预警模块
- 联调处方模块

推荐联调顺序：

1. 药品列表与详情
2. 库存入库、库存列表、库存流水
3. 低库存与临期预警
4. 处方创建与详情
5. 医生授权、审核、发药完整链路

产出物：

- 联调完成的前后端代码
- 联调问题修复
- 文档更新

验收标准：

- 药品页面可完成增删改查核心动作
- 库存页面可完成入库、出库、盘点
- 预警页面能展示真实数据
- 处方页面能完成授权、审核、发药

参考文档：

- `docs/frontend-integration.md`
- `docs/api.md`

## 5. 主功能验收清单

项目落地前，必须逐项确认以下主功能：

- 药品可新增、查询、修改、删除
- 库存可入库、出库、盘点
- 库存流水可查询
- 低库存预警可查询
- 临期/过期预警可查询
- 医生可直接创建处方
- 药师可代开发起处方
- 医生可授权或拒绝代开
- 药师可审核处方
- 药师可发药
- 发药后库存会扣减
- 发药后库存流水会写入

## 6. 每阶段统一交付要求

每完成一个阶段，至少交付：

- 代码
- 测试
- 文档
- 验证结果

如果缺少其中任意一项，不算阶段完成。

## 7. 当前建议的下一步

当前最合理的下一步不是继续扩散文档，而是继续恢复编码，并严格按以下顺序推进：

1. 完成前端统一请求头注入
2. 开始药品管理页面与真实 API 联调
3. 药品、库存、预警、处方页面联调
4. Docker 演示验证
