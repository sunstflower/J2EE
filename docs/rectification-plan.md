# 项目整改设计

## 1. 目标

本说明用于收口当前项目中“已能运行但尚不适合交付演示”的问题，并把后续整改路径固定下来。

本轮整改只聚焦三类问题：

- 容器化与部署交付仍缺少完整回归闭环
- 后端认证上下文尚未完全接管操作者字段
- 前端结构、交互和技术栈说明与当前实现存在明显偏差

## 2. 当前问题结论

### 2.1 已完成但需重新定性

以下内容已经具备基础实现，但不能直接等价视为“最终完成”：

- `docker compose up --build -d` 已完成实跑
- 容器已能启动并提供 `localhost:3000` 统一入口
- 前后端主链路已完成最小联调

但当前仍缺少：

- 基于演示脚本的完整人工验收记录
- 部署交付视角的回归清单
- 对前端结构性问题的收口整改

### 2.2 当前必须承认的偏差

#### 偏差一：前端没有真正落地路由

当前实现：

- `HomePage` 直接顺序渲染：
  - `DrugPage`
  - `InventoryPage`
  - `WarningPage`
  - `PrescriptionPage`

问题：

- 单页过长，演示入口不清晰
- 角色导航缺失
- 与 `docs/frontend-integration.md` 中已经写明的路由结构不一致

整改原则：

- 引入 `react-router`
- 改为“壳层布局 + 导航 + 分页模块”的结构
- 文档与代码必须统一，不允许继续保留“文档有路由、代码无路由”的状态

#### 偏差二：前端技术栈描述与实现不一致

当前文档写法：

- `React + Vite + shadcn/ui`

当前真实实现：

- `React + Vite + 原生 CSS`
- `package.json` 中没有 `Tailwind CSS`
- 没有 `shadcn/ui`
- 没有任何第三方组件库
- 页面样式主要由 `frontend/src/styles.css` 手写维护

整改原则：

- 二选一，不允许继续模糊：
  - 方案 A：补齐 `Tailwind CSS + shadcn/ui`
  - 方案 B：文档改为“原生 CSS，自定义组件”

当前推荐：

- 以项目落地效率为先，优先选择方案 B
- 先完成路由、导航、确认弹窗、分页、统一状态处理
- 不在当前阶段为了“追技术栈名义一致”引入整套组件库并扩大改造面

#### 偏差三：删除操作没有二次确认

当前问题：

- 药品删除是直接提交
- 演示误触风险高

整改原则：

- 所有删除类操作必须增加二次确认
- 若当前不引入组件库，可先使用轻量确认弹层或浏览器 `confirm`
- 后续若统一组件体系，再切换为对话框组件

#### 偏差四：页面状态管理重复

当前问题：

- 每个页面都重复维护：
  - `loading`
  - `submitting`
  - `message`
  - `errorMessage`

影响：

- 提示行为不一致
- 页面逻辑冗余
- 后续维护成本高

整改原则：

- 抽取统一请求动作与资源加载 Hook
- 最小目标：
  - `useApiAction`
  - `usePagedResource`

本阶段不强制引入 React Query，但应为后续接入保留接口边界

#### 偏差五：分页参数存在但没有分页 UI

当前问题：

- 查询参数已包含 `pageNum` / `pageSize`
- 页面只展示“共 X 条”
- 没有上一页、下一页、页码切换

整改原则：

- 所有分页列表页都必须补分页控件
- 第一阶段只要求：
  - 上一页
  - 下一页
  - 当前页号
  - 总条数

#### 偏差六：角色差异没有在导航层体现

当前问题：

- 医生和药师进入同一长页面
- 只有处方页内的操作按钮按角色变更

整改原则：

- 角色差异要前移到导航层
- 医生和药师至少在导航可见项、默认首页和页面提示上存在差异

推荐导航策略：

- 医生：
  - 药品管理
  - 库存管理
  - 预警查询
  - 处方工作台
- 药师：
  - 库存管理
  - 预警查询
  - 处方工作台
  - 药品管理可保留只读入口，或显式标记为维护类功能

#### 偏差七：后端操作者字段仍未完全收口

当前问题：

- 部分请求仍由前端传：
  - `createdByUserId`
  - `createdByName`
  - `createdByRole`
  - `operatorId`
  - `operatorName`

影响：

- 容易被前端绕过
- 与认证接入目标不一致

整改原则：

- 后端从认证上下文读取操作者信息
- 前端只保留业务字段，不再手填操作者字段
- 先改处方、库存两个强依赖操作者的模块

## 3. 整改目标状态

整改完成后，应达到以下目标：

- 浏览器入口为路由化应用，而不是长滚动工作台
- 文档中声明的前端结构与实际实现一致
- 删除操作具备二次确认
- 所有分页列表可翻页
- 页面公共状态提示机制统一
- 角色差异在导航层可见
- 后端操作者字段由认证上下文统一接管
- Docker 与部署说明包含一轮真实演示验收记录

## 4. 推荐整改顺序

### 阶段一：文档对齐

目标：

- 先冻结整改目标，避免继续按旧结构开发

执行项：

- 修正 README 中前端技术栈描述
- 修正前端联调文档中的“当前状态”说明
- 补充本整改设计文档
- 更新执行清单

### 阶段二：前端结构整改

目标：

- 从“长页面堆叠”切换到“路由化壳层”

执行项：

- 引入 `react-router-dom`
- 增加应用布局组件
- 增加侧边栏或顶部导航
- 将 4 个业务模块改为独立路由页面
- 将角色差异前移到导航层

验收标准：

- 任一模块可通过独立 URL 访问
- 不再依赖 `HomePage` 长页面滚动
- 医生/药师入口可见差异明确

### 阶段三：前端交互收口

目标：

- 补齐演示阶段最容易暴露的问题

执行项：

- 增加删除确认
- 增加分页控件
- 抽取统一状态管理 Hook
- 统一成功/失败提示

验收标准：

- 删除操作无误触直删
- 所有分页接口都有可见翻页入口
- 页面提示逻辑一致

### 阶段四：认证上下文收口

目标：

- 后端不再信任前端传入的操作者字段

执行项：

- 库存模块改为从上下文读取 `operator`
- 处方模块改为从上下文读取 `createdBy*` 与审核/发药操作者
- 更新接口文档与测试

验收标准：

- 前端请求体中移除操作者相关字段后仍可正常完成链路
- 越权伪造操作者身份被后端拒绝

### 阶段五：容器化与部署回归

目标：

- 从“容器可启动”提升到“交付可复现”

执行项：

- 按演示脚本走一轮完整人工验收
- 记录医生、药师两条演示路径
- 补充部署回归结果
- 固化启动、停止、重置、验收命令

验收标准：

- 一台具备 Docker 的机器可完整复现
- 演示链路有明确通过记录
- 文档可指导第三方完成启动和验收

## 5. 当前推荐决策

为避免整改面失控，当前建议明确以下决策：

1. 前端先补路由和导航，不先引入大型 UI 体系
2. README 与架构文档先按真实实现改成“React + Vite + 原生 CSS”
3. 删除确认先用轻量实现，不等待组件库落地
4. 公共状态管理先抽 Hook，不急于引入 React Query
5. 认证上下文收口优先处理库存和处方

## 6. 风险说明

- 如果先引入组件库再做路由整改，改造面会显著扩大
- 如果不先修正文档，后续评审会持续质疑“设计与实现不一致”
- 如果继续保留前端手填操作者字段，认证方案会长期停留在半完成状态
