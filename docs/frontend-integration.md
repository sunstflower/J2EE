# 前端联调约定

## 1. 目标

本说明用于约束前端落地范围，避免页面实现偏离主功能。

联调目标只围绕四个主模块：

- 药品管理
- 库存管理
- 预警查询
- 处方管理

## 2. 页面清单

当前建议最小页面集合如下：

### 2.1 登录页

用途：

- 选择医生或药师身份
- 建立当前用户上下文

### 2.2 首页

用途：

- 展示主模块入口
- 展示系统当前可演示能力

### 2.3 药品列表页

对应能力：

- 药品分页查询
- 药品详情查看
- 药品新增
- 药品编辑
- 药品删除

### 2.4 库存管理页

对应能力：

- 库存分页查询
- 库存详情查看
- 库存入库
- 库存出库
- 库存盘点

### 2.5 库存流水页

对应能力：

- 查询库存流水

### 2.6 预警页

对应能力：

- 低库存预警
- 临期预警
- 过期预警

### 2.7 处方工作台页

对应能力：

- 处方分页查询
- 状态筛选
- 查看处方详情
- 医生授权/拒绝
- 医生提交草稿
- 审核通过/驳回
- 发药
- 取消
- 医生直接建方
- 药师代开发起

## 3. 推荐路由结构

建议采用以下最小路由：

- `/login`
- `/`
- `/drugs`
- `/inventories`
- `/inventories/records`
- `/warnings`
- `/prescriptions`
- `/prescriptions/new`
- `/prescriptions/:id`

## 4. 前后端联调顺序

建议按以下顺序联调：

1. 登录页与当前用户状态
2. 药品列表页
3. 库存页与库存流水页
4. 预警页
5. 处方列表页
6. 处方创建页
7. 处方详情页中的授权、审核、发药操作

## 5. API 调用约定

前端调用 API 时建议统一：

- 使用一个请求封装层
- 统一处理基础 URL
- 统一附带当前用户请求头
- 统一处理错误提示

推荐约定：

- 所有接口通过同一个 `api client` 发起
- 页面组件不直接拼接请求头
- 页面组件只负责传业务参数

当前已落地约定：

- 前端已提供统一 `api client`
- 当前用户请求头由请求层自动注入
- 默认后端基地址为 `http://localhost:8080`
- `X-User-Name` 使用 URL 编码后再放入请求头，后端负责解码

当前已完成联调页面：

- 首页中的药品模块联调页
  - 已支持药品列表查询
  - 已支持药品新增
  - 已支持药品删除
- 首页中的库存模块联调页
  - 已支持库存分页查询
  - 已支持库存流水查询
  - 已支持入库、出库、盘点
  - 已通过当前登录用户自动注入 `operatorName`
- 首页中的预警模块联调页
  - 已支持低库存预警查询
  - 已支持临期 / 过期预警查询
  - 已支持自定义临期天数筛选
- 首页中的处方模块联调页
  - 已支持处方分页查询、详情查看与状态筛选
  - 已支持医生直接建方与药师代开发起
  - 已支持医生授权/拒绝、提交审核、药师审核、发药、取消
  - 已自动根据当前登录角色显示可操作按钮

后续继续保持：

- 处方页面复用同一请求层
- 页面内不重复处理当前用户头信息
- 当前工作台实现未引入独立路由，后续如需拆分页面应保持同一接口契约与角色约束

## 6. 页面级联动要求

### 6.1 药品与库存

- 库存操作必须可选择药品
- 入库成功后应能回到库存列表并看到结果

### 6.2 库存与预警

- 库存变更后应能在预警页面体现效果

### 6.3 处方与库存

- 发药成功后应能在库存页面或库存流水页看到扣减结果

### 6.4 处方与角色

- 医生和药师看到的可操作按钮应不同
- 未授权处方不能展示审核或发药操作入口

## 7. 最小 UI 目标

当前前端阶段不追求复杂视觉，而优先保证：

- 页面可访问
- 表单可提交
- 列表可展示
- 状态可区分
- 主流程可走通

## 8. 前端阶段验收标准

前端联调完成时，至少满足：

- 医生可直接建方并走完整链路
- 药师可代开发起并等待医生授权
- 库存入库、出库、盘点可在页面完成
- 预警页面能展示低库存与临期数据
- 发药后能看到库存扣减结果

当前阶段已通过：

- 当前用户登录态可建立并切换
- 药品页面可通过统一请求层访问真实接口契约
- 库存页面可通过统一请求层完成查询、入库、出库、盘点和流水联调
- 预警页面可通过统一请求层完成低库存与效期预警查询
- 处方页面可通过统一请求层完成建方、授权、审核、发药、取消主链路联调
